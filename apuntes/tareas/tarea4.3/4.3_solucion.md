# **Solución 4.3: Instalación de Apache Tomcat como servicio de SystemD**

### **Descripción de la tarea**

Apache Tomcat es un servidor de aplicaciones web escritas en Java: ejecuta aplicaciones empaquetadas como ficheros `.war` y las sirve por HTTP. A diferencia del servidor Apache de la tarea 4.2, en esta tarea **no se instalará con `apt`**, sino desde el **binario oficial** (`.tar.gz`) publicado por el proyecto, tal como se hace con mucho software de terceros en entornos reales.

Al no venir de un paquete de Debian, Tomcat no trae ningún servicio de SystemD. Será el administrador quien tenga que ubicarlo en `/opt`, crear un usuario propio para ejecutarlo y escribir su **unidad de SystemD**, para poder gestionarlo con `systemctl` igual que cualquier otro servicio y que arranque solo con el sistema. Por último, se habilitará la aplicación de administración web **Manager** con un usuario propio.

La tarea se realiza en una máquina **Debian 13** y se instala la versión **Tomcat 11**. Todos los comandos se ejecutan como `root`.

_*Nota*_: Tomcat está escrito en Java, así que, a diferencia del Apache compilado en el documento 27, **no hay que compilar nada**. El `.tar.gz` ya contiene los programas listos para ejecutar: lo que hace falta es una máquina virtual de Java que los ejecute.

### **Pasos de la tarea**

1. Instalar Java (Tomcat 11 necesita Java 17 o superior) y comprobar la versión instalada.

Debian 13 incluye OpenJDK 21. Basta con el entorno de ejecución (`jre`) en su variante `headless`, sin componentes gráficos, que es la adecuada para un servidor:

```bash
root@debian:~# apt update && apt install openjdk-21-jre-headless -y
root@debian:~# java -version
openjdk version "21.0.8" 2025-07-15
OpenJDK Runtime Environment (build 21.0.8+9-Debian-1)
OpenJDK 64-Bit Server VM (build 21.0.8+9-Debian-1, mixed mode, sharing)
```

_*Nota*_: La versión exacta de Java puede variar según las actualizaciones de Debian; lo importante es que sea la 17 o superior.

2. Crear un usuario de sistema llamado `tomcat`, sin posibilidad de iniciar sesión, que será el que ejecute el servicio.

```bash
root@debian:~# useradd -r -s /usr/sbin/nologin -d /opt/tomcat tomcat
root@debian:~# id tomcat
uid=999(tomcat) gid=999(tomcat) grupos=999(tomcat)
```

| Opción | Significado |
|---|---|
| `-r` | Crea una cuenta **de sistema** (UID bajo, sin caducidad de contraseña), pensada para servicios y no para personas. |
| `-s /usr/sbin/nologin` | Le asigna una shell que rechaza el inicio de sesión: nadie puede entrar en la máquina como `tomcat`. |
| `-d /opt/tomcat` | Define su directorio personal, que será el de la instalación. |

_*Nota*_: Un servicio nunca debe ejecutarse como `root`. Si un atacante aprovecha una vulnerabilidad de Tomcat o de una aplicación desplegada en él, obtendrá los permisos del usuario que lo ejecuta. Con un usuario propio y sin shell, el daño queda limitado a lo que ese usuario puede tocar.

3. Descargar en `/usr/local/src` el binario de Tomcat 11 y su suma de comprobación SHA-512 desde la web de Apache, y verificar la integridad del fichero descargado.

```bash
root@debian:~# cd /usr/local/src
root@debian:/usr/local/src# wget https://archive.apache.org/dist/tomcat/tomcat-11/v11.0.26/bin/apache-tomcat-11.0.26.tar.gz
root@debian:/usr/local/src# wget https://archive.apache.org/dist/tomcat/tomcat-11/v11.0.26/bin/apache-tomcat-11.0.26.tar.gz.sha512
root@debian:/usr/local/src# sha512sum -c apache-tomcat-11.0.26.tar.gz.sha512
apache-tomcat-11.0.26.tar.gz: OK
```

_*Nota*_: Si `sha512sum -c` no devuelve `OK`, el fichero está dañado o manipulado y no debe usarse. Con `apt` esta comprobación se hace sola; al descargar a mano es responsabilidad del administrador.

_*Nota*_: Se usa `archive.apache.org` porque conserva todas las versiones y el enlace no caduca. La versión más reciente de la rama 11 se consulta en https://tomcat.apache.org/download-11.cgi; en producción se instala siempre la última.

4. Descomprimir Tomcat en `/opt` y crear el enlace simbólico `/opt/tomcat` apuntando al directorio de la versión instalada.

```bash
root@debian:/usr/local/src# tar -xzf apache-tomcat-11.0.26.tar.gz -C /opt
root@debian:/usr/local/src# ln -s /opt/apache-tomcat-11.0.26 /opt/tomcat
root@debian:/usr/local/src# ls -l /opt
drwxr-xr-x  9 root root 4096 oct  6 11:52 apache-tomcat-11.0.26
lrwxrwxrwx  1 root root   26 oct  6 11:52 tomcat -> /opt/apache-tomcat-11.0.26
root@debian:/usr/local/src# ls /opt/tomcat
bin  BUILDING.txt  conf  CONTRIBUTING.md  lib  LICENSE  logs  NOTICE  README.md  RELEASE-NOTES  RUNNING.txt  temp  webapps  work
```

| Directorio | Contenido |
|---|---|
| `bin/` | Scripts de arranque y parada (`startup.sh`, `shutdown.sh`, `catalina.sh`). |
| `conf/` | Configuración: `server.xml` (puertos), `tomcat-users.xml` (usuarios)... |
| `lib/` | Bibliotecas Java (`.jar`) del propio Tomcat. |
| `logs/` | Registros, con `catalina.out` como log principal. |
| `webapps/` | Aplicaciones desplegadas: cada `.war` o directorio es una aplicación. |
| `work/`, `temp/` | Ficheros de trabajo y temporales que genera Tomcat en ejecución. |

_*Nota*_: El enlace simbólico es la clave para actualizar sin tocar nada más. Toda la configuración (la unidad de SystemD, los scripts) apunta a `/opt/tomcat`. Para pasar a una versión nueva basta con descomprimirla junto a la anterior y cambiar el enlace; si algo falla, se vuelve a apuntar a la antigua. Es la misma idea de tener varias versiones en `/opt` que se vio en el documento 27.

5. Ajustar el propietario y los permisos de la instalación para que el usuario `tomcat` solo pueda escribir donde lo necesita.

Tomcat se distribuye con permisos muy cerrados: todo pertenece a `root`, el directorio `conf/` solo es accesible para su propietario (`700`) y sus ficheros solo él los puede leer (`600`). Tal como está, el usuario `tomcat` no podría ni leer su propia configuración:

```bash
root@debian:~# ls -ld /opt/apache-tomcat-11.0.26/conf
drwx------ 2 root root 4096 sep  9 23:36 /opt/apache-tomcat-11.0.26/conf
```

Se ajusta así:

```bash
root@debian:~# cd /opt/apache-tomcat-11.0.26
root@debian:/opt/apache-tomcat-11.0.26# chown -R root:tomcat .
root@debian:/opt/apache-tomcat-11.0.26# chmod -R g+r conf
root@debian:/opt/apache-tomcat-11.0.26# chmod g+x conf
root@debian:/opt/apache-tomcat-11.0.26# mkdir -p conf/Catalina/localhost
root@debian:/opt/apache-tomcat-11.0.26# chown -R tomcat:tomcat conf/Catalina logs temp webapps work
```

| Ruta | Propietario | Motivo |
|---|---|---|
| Toda la instalación | `root:tomcat` | Los programas y la configuración son de `root`. El grupo `tomcat` puede leerlos y ejecutarlos, pero **no modificarlos**. |
| `conf/` | `root:tomcat`, lectura para el grupo | `g+r` permite al grupo leer los ficheros y `g+x` atravesar el directorio. Tomcat lee su configuración, pero no puede cambiarla. |
| `conf/Catalina/` | `tomcat:tomcat` | Tomcat guarda aquí la configuración de cada aplicación desplegada, así que necesita escribir. Si no existe, intenta crearlo al arrancar. |
| `logs/`, `temp/`, `webapps/`, `work/` | `tomcat:tomcat` | El resto de sitios donde Tomcat necesita escribir. |

_*Nota*_: La tentación es hacer `chown -R tomcat:tomcat` sobre todo el directorio, y funciona, pero entonces una aplicación comprometida podría reescribir los scripts de `bin/` o la configuración de `conf/`. Separar «lo que se ejecuta» de «lo que se escribe» es la práctica que recomienda la propia guía de seguridad de Tomcat.

6. Localizar la ruta de instalación de Java (`JAVA_HOME`), que necesitará la unidad de SystemD.

`/usr/bin/java` es en realidad una cadena de enlaces simbólicos. `readlink -f` la sigue hasta el final:

```bash
root@debian:~# readlink -f /usr/bin/java
/usr/lib/jvm/java-21-openjdk-amd64/bin/java
```

`JAVA_HOME` es el directorio de Java, es decir, la ruta anterior sin `/bin/java`: `/usr/lib/jvm/java-21-openjdk-amd64`.

7. Crear la unidad de SystemD `tomcat.service`.

Las unidades creadas por el administrador se guardan en `/etc/systemd/system/`, a diferencia de las que instalan los paquetes, que están en `/lib/systemd/system/`. Se crea el fichero `/etc/systemd/system/tomcat.service`:

```ini
[Unit]
Description=Apache Tomcat 11
After=network.target

[Service]
Type=forking
User=tomcat
Group=tomcat
Environment="JAVA_HOME=/usr/lib/jvm/java-21-openjdk-amd64"
Environment="CATALINA_HOME=/opt/tomcat"
Environment="CATALINA_BASE=/opt/tomcat"
Environment="CATALINA_PID=/opt/tomcat/temp/tomcat.pid"
PIDFile=/opt/tomcat/temp/tomcat.pid
ExecStart=/opt/tomcat/bin/startup.sh
ExecStop=/opt/tomcat/bin/shutdown.sh
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

| Directiva | Significado |
|---|---|
| `After=network.target` | Arranca después de que la red esté configurada. |
| `Type=forking` | `startup.sh` lanza Java en segundo plano y termina; SystemD debe seguir al proceso que queda en marcha. |
| `User` / `Group` | Ejecuta Tomcat con el usuario sin privilegios del paso 2, no como `root`. |
| `Environment` | Variables que necesita Tomcat: dónde está Java (`JAVA_HOME`), dónde está Tomcat (`CATALINA_HOME`, `CATALINA_BASE`) y dónde guardar su PID (`CATALINA_PID`). |
| `PIDFile` | Fichero con el PID del proceso de Java, para que SystemD sepa cuál vigilar. Está en `temp/`, donde `tomcat` puede escribir. |
| `ExecStart` / `ExecStop` | Scripts de arranque y parada que trae Tomcat. |
| `Restart=on-failure` | Si Tomcat se cae por un fallo, SystemD lo vuelve a levantar. |
| `WantedBy=multi-user.target` | Una vez habilitado, arranca con el sistema. |

_*Nota*_: Una alternativa igual de válida es `Type=simple` con `ExecStart=/opt/tomcat/bin/catalina.sh run`. En ese caso Tomcat se queda en primer plano, SystemD lo vigila directamente sin necesidad de `PIDFile` y su salida va al diario de SystemD. Se usa aquí `forking` por ser el arranque que trae Tomcat de serie, el mismo tipo que el Apache compilado del documento 27.

8. Recargar SystemD, habilitar el servicio para que arranque con el sistema, iniciarlo y comprobar su estado.

```bash
root@debian:~# systemctl daemon-reload
root@debian:~# systemctl enable --now tomcat
Created symlink '/etc/systemd/system/multi-user.target.wants/tomcat.service' → '/etc/systemd/system/tomcat.service'.
root@debian:~# systemctl status tomcat
● tomcat.service - Apache Tomcat 11
     Loaded: loaded (/etc/systemd/system/tomcat.service; enabled; preset: enabled)
     Active: active (running) since lun 2026-10-06 12:04:18 CEST; 6s ago
    Process: 2398 ExecStart=/opt/tomcat/bin/startup.sh (code=exited, status=0/SUCCESS)
   Main PID: 2412 (java)
      Tasks: 30 (limit: 2306)
     Memory: 118.4M
        CPU: 4.112s
     CGroup: /system.slice/tomcat.service
             └─2412 /usr/lib/jvm/java-21-openjdk-amd64/bin/java -Djava.util.logging.config.file=/opt/tomcat/conf/logging.properties ...
```

_*Nota*_: `daemon-reload` es obligatorio cada vez que se crea o modifica una unidad: SystemD lee las unidades al arrancar y no se entera de los cambios hasta que se le pide. `enable --now` habilita e inicia el servicio en un solo paso. En el estado se ve que `startup.sh` terminó (`code=exited`) y que el proceso principal que queda es `java`, tal como se indicó con `Type=forking`.

9. Comprobar en qué puertos escucha Tomcat y que responde a las peticiones web, tanto desde la propia máquina como desde un navegador.

```bash
root@debian:~# ss -tlnp | grep java
LISTEN 0  100        *:8080               *:*  users:(("java",pid=2412,fd=43))
LISTEN 0  1   [::ffff:127.0.0.1]:8005     *:*  users:(("java",pid=2412,fd=52))
root@debian:~# curl -I http://localhost:8080
HTTP/1.1 200
Content-Type: text/html;charset=UTF-8
```

| Puerto | Uso |
|---|---|
| `8080` | Conector HTTP: por él llegan las peticiones web. Escucha en todas las interfaces (`*`). |
| `8005` | Puerto de apagado: `shutdown.sh` se conecta a él para ordenar a Tomcat que se pare. Solo escucha en `127.0.0.1`, para que nadie pueda apagar Tomcat desde la red. |

Desde el navegador del equipo anfitrión, en `http://IP_DE_LA_VM:8080`, aparece la página de bienvenida de Tomcat.

_*Nota*_: Si la máquina tiene el cortafuegos `ufw` activo (documento 44), hay que abrir el puerto: `ufw allow 8080/tcp`.

10. Consultar los registros del servicio, tanto en el diario de SystemD como en los ficheros de log de Tomcat.

```bash
root@debian:~# journalctl -u tomcat -n 5
oct 06 12:04:17 debian systemd[1]: Starting tomcat.service - Apache Tomcat 11...
oct 06 12:04:18 debian startup.sh[2398]: Tomcat started.
oct 06 12:04:18 debian systemd[1]: Started tomcat.service - Apache Tomcat 11.
root@debian:~# tail -n 3 /opt/tomcat/logs/catalina.out
06-Oct-2026 12:04:19.871 INFORMACIÓN [main] org.apache.coyote.AbstractProtocol.start Starting ProtocolHandler ["http-nio-8080"]
06-Oct-2026 12:04:19.902 INFORMACIÓN [main] org.apache.catalina.startup.Catalina.start Server startup in [1043] milliseconds
```

_*Nota*_: Con `Type=forking`, el diario de SystemD solo recoge el arranque y la parada del servicio; los mensajes del propio Tomcat van a sus ficheros de `logs/`. Si Tomcat no arranca, el motivo casi siempre está en `catalina.out`, por ejemplo un `Address already in use` si el puerto 8080 ya está ocupado.

11. Crear un usuario con permiso para acceder a la aplicación Manager y comprobar el acceso desde la propia máquina, con y sin credenciales.

El Manager es una aplicación web incluida con Tomcat que permite desplegar, parar y retirar aplicaciones desde el navegador. Por seguridad viene **sin ningún usuario**, así que hay que crearlo en `conf/tomcat-users.xml`, dentro de la etiqueta `<tomcat-users>`:

```xml
<tomcat-users ...>
  <role rolename="manager-gui"/>
  <user username="admin" password="CambiaEstaClave" roles="manager-gui"/>
</tomcat-users>
```

El rol `manager-gui` da acceso a la interfaz web del Manager. Tomcat solo lee este fichero al arrancar, así que hay que reiniciar el servicio:

```bash
root@debian:~# systemctl restart tomcat
root@debian:~# curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8080/manager/html
401
root@debian:~# curl -s -o /dev/null -w '%{http_code}\n' -u admin http://localhost:8080/manager/html
Enter host password for user 'admin':
200
```

Sin credenciales se obtiene un `401` (no autenticado); con el usuario creado, un `200`.

_*Nota*_: La contraseña se guarda en texto plano en `tomcat-users.xml`. Por eso ese fichero solo es legible por `root` y el grupo `tomcat` (paso 5). Con `curl -u admin`, sin escribir la contraseña, `curl` la pide por teclado y no queda registrada en el historial (documento 33).

12. Intentar acceder al Manager desde el navegador del equipo anfitrión, explicar por qué se deniega el acceso y permitirlo únicamente desde la red del laboratorio.

Desde el navegador del anfitrión, `http://IP_DE_LA_VM:8080/manager/html` devuelve **403 Access Denied**, aunque el usuario y la contraseña sean correctos. La razón está en `webapps/manager/META-INF/context.xml`, que restringe el acceso por dirección IP:

```xml
<Valve className="org.apache.catalina.valves.RemoteCIDRValve"
       allow="127.0.0.0/8,::1/128" />
```

El atributo `allow` es una lista, separada por comas, de las redes permitidas en notación CIDR (documento 31): `127.0.0.0/8` es el bucle local en IPv4 y `::1/128` en IPv6. Es decir, solo se admite la propia máquina. Como el Manager permite desplegar código en el servidor, Tomcat lo protege por partida doble: **quién eres** (usuario y contraseña) y **desde dónde te conectas** (IP).

Para permitir el acceso desde la red del laboratorio, por ejemplo la red solo-anfitrión `192.168.56.0/24` de VirtualBox, se añade esa red a la lista:

```xml
<Valve className="org.apache.catalina.valves.RemoteCIDRValve"
       allow="127.0.0.0/8,::1/128,192.168.56.0/24" />
```

_*Nota*_: En muchas guías de Internet, escritas para versiones anteriores de Tomcat, esta línea aparece como `RemoteAddrValve` con una expresión regular del tipo `allow="127\.\d+\.\d+\.\d+|::1"`. Las dos válvulas cumplen la misma función; Tomcat 11 trae de serie `RemoteCIDRValve`, más legible. Conviene editar siempre la línea que aparezca realmente en el fichero, no la de la guía.

```bash
root@debian:~# systemctl restart tomcat
```

Tras reiniciar, el navegador del anfitrión pide usuario y contraseña y, con las credenciales del paso 11, muestra el Manager.

_*Nota*_: Nunca se debe abrir el Manager a cualquier dirección (por ejemplo, añadiendo `0.0.0.0/0`, que equivale a «todo Internet»). Un Manager expuesto a Internet con una contraseña débil es una de las vías de ataque más conocidas contra Tomcat: quien entra puede desplegar un `.war` malicioso y ejecutar código en el servidor. Se abre solo a la red concreta desde la que se administra.

13. Reiniciar la máquina y comprobar que Tomcat se inicia automáticamente.

```bash
root@debian:~# reboot
...
root@debian:~# systemctl is-enabled tomcat
enabled
root@debian:~# systemctl is-active tomcat
active
```

Tomcat arranca solo gracias a `systemctl enable` (paso 8), que creó el enlace en `multi-user.target.wants/`. Se ha conseguido que un programa instalado a mano, fuera de `apt`, se comporte exactamente igual que cualquier servicio del sistema.
